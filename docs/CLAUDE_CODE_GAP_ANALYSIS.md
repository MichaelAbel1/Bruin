# Bruin 距离 Claude Code 还有多远

后续开发请使用[分阶段实施清单](IMPROVEMENT_ROADMAP.md)。清单汇总了下文各轮发现、当前修复状态、依赖、源码位置和验收方法。下文的复现与测试数字均对应各轮检查时的工作树。

评估日期为 2026-11-19。基线为 Bruin 0.12.1，分支 `codex/pi-inspired-improvements`，HEAD 为 `9c5c35a`，**包含当时工作区尚未提交的实现和测试**。比较目标选为个人开发者在已有仓库中完成“理解需求 → 跨文件修改 → 验证 → 审核或撤回”的日常工作。Claude Code 一侧采用 Anthropic 公开的产品行为说明。[官方产品概览](https://code.claude.com/docs/en/overview)

## 多 Agent 专项：并行委派和团队协作

**独立分工已经能用，需要边做边协商的任务仍有明显差距。** 例如，让两个 Agent 分别排查前端和后端，再由主 Agent 汇总，Bruin 已有完整执行路径。若后端 Agent 在执行中更改接口约定，前端 Agent 需要马上收到变更、确认版本，并用两边的最终代码跑联合测试，当前 Bruin 的流程还要靠主 Agent 或用户接力。

Claude Code 有两个可比对象。常规 **subagents** 适合有边界的委派，可配置角色、模型和工具，命名的子 Agent 也可互发消息。**Agent Teams** 让独立会话通过队内消息和共享任务列表协调，用户可直接指导成员。Teams 是默认关闭的实验功能，启动队员要求交互式会话；恢复主会话也不会恢复原来的进程内队员。对标时应分别衡量这两种体验。[Claude Code 子 Agent](https://code.claude.com/docs/en/sub-agents) · [Agent Teams 的比较与限制](https://code.claude.com/docs/en/agent-teams)

### 多 Agent 的改进顺序与验收

1. **先让两个 Agent 的代码能一起交付。** 修复托管工作树索引，委派时列出基线提交和父目录已有修改，返回补丁、变更路径、实际测试结果及阻塞项。用“一个改接口，一个改调用方，父目录已有用户编辑”验收。临时集成应能暴露不兼容，未获确认前父目录保持原状；失败后两份提案均可取回。
2. **让运行中的成员能接收纠正。** 复用现有持久事件和输入队列，先做父到子的定向交付，再做同队成员之间的消息。记录发送者、接收者、任务和是否已消费。用“B 已开工，A 更正字段名”验收：B 在下一次可处理输入时看见更正；重启后不重复消费、跨团队不串消息，成员发来的文本不能授予工具权限。
3. **有了协作数据，再决定并发规模。** 在原有任务图上关联成员、依赖和成果，汇总父子用量，给新委派设团队预算。以同一模型、同一提交分别跑单 Agent、双 Agent 和 Claude Code 对照；将独立排查、跨模块实现、同文件冲突分开统计。看最终联合测试通过率、从开始到可合入的耗时、人工协调次数和总 token。若增加成员只缩短各自编码时间，却拉长集成时间，保留两人上限。

**本次专项验证。** 当前工作树构建通过。重跑工作树、结果投递、恢复和桌面协作四组测试，两轮均为 31 项中 30 通过、1 失败。单独运行失败用例也能复现：在真实 Git 子工作树的仓库子目录中，文件读写和父目录保留检查通过，但索引预期返回 `scoped.txt`，实际返回空列表。这补充了前文使用模拟目录布局得到的证据。上述测试使用模拟模型，本次没有两款产品的真实任务速度或成本数据。[失败用例](../src/tests/subagent-worktree.test.ts) · [索引过滤](../src/core/repository-index.ts) · [桌面协作测试](../src/tests/desktop-collaboration.test.ts)

## 上下文、记忆沉淀与推理开销

这三项直接影响用户要不要重复交代同一件事。一次会话内，应保住用户的目标、更正与验收条件；新会话只需取回与当前任务相关、仍然有效的经验；证据已经足够时，Agent 应能停止调查并交付。以下按当前工作树复核，实验使用临时 SQLite 和模拟模型，无需调用收费 API。

### 上下文：压缩后，关键约束还在模型眼前吗？

Bruin 已有估算 token、工具定义开销、单轮用量校准、历史摘要和工具结果截断。SQLite 保存原始事件，桌面显示累计用量。**累计用量不能回答“下一次请求会带上什么”**。Claude Code 的 `/context` 能查看窗口组成，`/compact` 支持用户指定要保留的重点。Bruin 可以借鉴这种可见性，同时保留自己的多供应商预算策略。[Bruin 提示组装](../src/core/agent.ts) · [历史与预算](../src/core/history.ts) · [Claude Code 命令](https://code.claude.com/docs/en/commands) · [定向压缩](https://code.claude.com/docs/en/troubleshooting)

**已复现的边界。** 在 8,192 token 窗口中，把一条唯一验收规则放在约两万字的合成中文请求中段，模拟摘要服务持续报错。真实 Runner 保留了 SQLite 用户原文，但持久摘要和最终发给模型的提示都没有该规则。处理这一次请求还尝试了 10 次分块摘要。这个结果对应“超长输入且摘要服务失败”的具体路径；正常摘要的遗漏率仍待实测。[摘要与回退实现](../src/core/agent.ts) · [预算回归测试](../src/tests/history.test.ts)

- **P1 · 先保住任务约束。** 让用户能把必须保留的原文或验收项固定到本任务，引用原始事件。压缩后重注入仍生效的条目，用户后续更正可以替代旧条目。必要信息超窗时提示用户选择保留范围。验收覆盖规则放首、中、尾，连续两次压缩，恢复会话，以及“先要求 A、后更正为 B”。
- **P1 · 看得见上下文去向。** 在发送前按指令、工具定义、记忆、附件、历史和本轮工具输出展示估算占用；指出刚压缩的部分、摘要是否回退，以及哪里能看原文。来源相同的摘要连续失败时，本轮余下分块直接走本地回退，并记录原因。以摘要调用次数、约束保留率和最终任务通过率共同验收。

### 记忆沉淀：记到哪里，下次又能否取回？

### 避免过度思考：分别控制模型推理和反复行动

**单次模型请求的推理强度。** Bruin 对兼容模型正文中的 `<think>` 做显示过滤；常规请求没有显式传入按模型配置的推理强度。隐藏文本不会改变已经发生的推理开销。Claude Code 在支持的模型上提供 effort 设置。建议先在确认支持的 Provider/模型上提供单次任务可改的档位，显示实际生效值；能力未知时沿用供应商默认。简单定位与复杂故障各做一组对照，记录首个可用答案延迟、供应商可提供的用量和独立验收通过率。不能从回答长短推断隐藏推理量。[模型网关](../src/providers/gateway.ts) · [Claude Code 推理强度](https://code.claude.com/docs/en/model-config#adjust-effort-level)

**多轮工具调用是否产生新证据。** Bruin 已有次数、时间上限和相同失败请求提示。用模拟模型连续六次请求读取同一文件、工具每次返回完全相同的成功结果，真实 Runner 接受了六次读取，第七次模型调用才由模拟模型主动结束。现有重复失败提示在此例中触发零次。这个实验验证了控制器边界，真实用户遇到这类循环的频率尚未测量。[重复失败检测](../src/core/agent.ts) · [现有控制用例](../src/tests/agent-control.test.ts)

建议先做**无进展提醒**：对同一目标、相同参数、相同输出且无中途修改的成功读取，提示模型利用已有证据给结论，或指明还缺哪项证据。必要验收尚未执行时继续验证；文件刚变更、翻到下一页、失败后修复再测试，均允许继续。在延迟、调用次数之外记录两项指标：验收已满足后仍发出的调用数，以及误停导致必须由用户再次催促的次数。待观测到收益，再决定是否允许用户设置更严格的停止条件。

**建议实施顺序。** 先修跨项目偏好和压缩后丢约束，再改续跑召回与摘要失败回退，随后加入无进展提醒和模型强度选项。首批直接复用上述四个合成场景作为回归样本；另加复杂任务作为反例，确保节省 token 的改动不会牺牲最终任务通过率。

**本轮验证。** 构建通过，上下文、记忆、用量和 Agent 控制四组现有测试共 36 项全部通过；上述四个合成场景为额外行为检查。复核上轮索引结论时，当前工作树已含托管目录索引修订，专项作用域用例通过。扩展到工作树和快照的六组测试合计 51 项，46 通过、5 失败，失败集中在写入、快照与子工作树结果路径。前文多 Agent 章节的 30/31 为上一轮工作树结果。尚未实测真实模型的压缩质量、推理耗时和费用。

## 两个值得先测量的性能问题

1. **热索引仍要读多少文件？** `searchRepository` 命中符号缓存前仍会打开候选文件、读取正文并计算哈希；扫描受 10,000 条路径、约 20 MB 正文和时间预算限制。大仓库里“没有命中”可能来自截断。先用固定的千文件和万文件仓库分别记录冷查、连续热查、单文件修改后的耗时、读取字节和目标命中率，再决定是否做增量更新。保留当前测试对“同大小、同时间戳改写”的检测能力，并把截断原因传到界面。[索引实现](../src/core/repository-index.ts) · [现有回归用例](../src/tests/repository-snapshots.test.ts)
2. **长会话的每次操作要重放多少历史？** 存储层 `events(id)` 按序取全量事件；Runner 一轮内多次调用，桌面队列和检查点通知还会发送完整视图。先用 1 千和 1 万事件，测首次打开、追加消息和恢复的 P95 延迟、峰值内存与 IPC 字节。若全量读传占主要成本，再用现有事件序号实现增量读取、视图投影和缺口补读。验收对比全量重建，覆盖乱序通知、切换会话和旧数据库。[事件存储](../src/storage/event-store.ts) · [桌面通知](../src/desktop-host.ts) · [快照顺序测试](../src/tests/event-snapshot.test.ts)

两项目前都是从代码读出的成本来源；本次没有测量真实用户仓库的耗时。新增索引依赖或改数据库结构，宜等基线证明收益后再决定。

## 怎样测出真实差距

建议把首次对照控制在 **12 道任务**。从可公开或已获授权的仓库固定提交中，各选 2 道仓库定位、局部修复、跨文件修改、失败测试诊断、中断恢复、子任务协作。每题预先写好验收条件和允许修改范围，保留 Agent 执行时看不到的独立检查。恢复题事先约定中断点与待保护文件。

- **控制变量。** 每次从相同的干净副本或同一份预制脏工作区开始，固定提示词、工具权限、人工审批脚本、时间上限与可供运行的测试。记录工具版本、实际模型 ID、推理设置及可见用量。同题每端跑 3 次；模型或运行条件无法匹配的结果单列，记录配置差异。先试跑两题检查判分规则。
- **判分。** 首要指标为独立验收通过且保住用户原有修改的次数，报告分子和分母；另记首次通过率、人工介入次数、完成耗时、中途放弃、可归属 token 与费用。恢复题增加“重复副作用次数”，协作题增加“成功接回且通过验证”。缺失用量标为未知。对每个失败保留基线提交、脱敏事件、最终 diff 和验收输出。
- **怎么用结果排期。** 如果大量失败出在找不到相关代码，先做仓库探索；若测试能过但用户改动丢失，优先修正写入与恢复。若两端都失败，先复核题目和环境。首次 12 题用于定位差距，小样本的平均分不宜外推为产品整体水平。
